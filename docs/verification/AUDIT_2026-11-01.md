# Audit: what A.I.N.D.Y. does, live, on 2026-11-01

**Written 2026-11-01**, on runtime 2.29.0 (image `998b66e88e09`, api recreated 16:40:25Z). It judges
what `INVENTORY.md` lists. This document is read-only: each fix is its own PR, and each retirement is
the owner's decision.

**The yardstick:** Infinity is the product (owner, 2026-08-01, reaffirmed 10-14). Every domain is
asked whether it **feeds the score**, **feeds the loop** (what the owner is told to do), is
**access** (a way in for the owner, other AIs or outside systems), or **feeds nothing**.

**Evidence used:**
- `scripts/inventory.py --live`, which gives rows per table;
- the newest write in each table;
- the owner's `user_scores` and `score_history`;
- `agent_runs` and `agent_steps`, `automation_logs`, `autonomy_decisions` and `release_handoffs`;
- the effective `AINDY_*` environment of the api container;
- test files per domain.

One limit: the api log only goes back to the 16:40Z recreate, so log-only evidence from before then
is the record in `RUNTIME_2_29_0_UPGRADE.md` §5.

## 3. What fails quietly

The 7th question, "does it fail visibly?", produced this audit's most useful finding:
**three of its findings were invisible to the owner until someone read a log or a table.**

- **Nodus fallback** (#2): 10 days of every scheduled run on Python, one WARNING line per run.
- **LLM credit exhaustion** (#3): a circuit open for about 90 minutes; drafts and embeddings deferred.
- **Release handoff no-run** (#4): it did send a "release stopped" email, and the email was wrong.

Below that sit the steady-state defaults: a KPI at neutral 50 for its whole life (#1), and a gate
that has never refused (#7). Each looks like a working system from the outside.

## 4. Owner decisions

- **D1, `focus_quality` (15% of the score).** Three options:
  - run a watcher client so the KPI has data;
  - re-weight the score while there is none;
  - or show the KPI as "no data" instead of 50.

  Today the score is 85% measured and 15% a constant.
- **D2, Goals.** Retire the Goals subsystem (routes, 3 registered jobs, 2 tables) in favour of the
  strategy layer, or wire it up. The house disposition so far is "park the backend, cut the UI".
  There's no UI here, so parking means leaving the jobs off the loop.
- **D3, the autonomy gate.** Is "always execute" the intended policy for these three scheduled
  triggers? If so, say so in the domain doc, so the gate isn't read as tested.
- **D4, Freelance.** Fourteen test files and 5,179 lines carry a domain that has never held a row.
  Keep it (the Worth axis is designed around it), park it, or retire it.
